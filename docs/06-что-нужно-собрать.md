# Полный перечень данных для статьи уровня Q1

Документ разбит на пять блоков. Блоки 1–2 определяют, будет ли статья
вообще. Блок 3 определяет, возьмёт ли её Q1-журнал или придётся идти
в Q3. Блоки 4–5 нужны для текста и для допуска к рецензированию.

---

## Порядок действий (критично)

```
1. Скачал данные из Moodle
2. Прогнал у СЕБЯ:  python3 scripts/anonymize_moodle_export.py папка
3. Проверил результат глазами
4. Прислал только обработанные файлы
```

Шаг 2 нельзя переносить на потом. Обезличивание после передачи не
отменяет самой передачи.

# БЛОК 1. Данные из Moodle — основа

Без любого пункта из этого блока исследование не складывается.

### 1.1 Логи учебной активности

**Что это:** записи о каждом действии студента в системе.

**Где взять:**
- через SQL — `ЗАПРОС 3` в `scripts/moodle_export_phpmyadmin.sql`
- через интерфейс — `Курс → Отчёты → Логи`, внизу «Скачать данные
  таблицы как» → CSV. Либо `Администрирование → Отчёты → Логи`

**Обязательные поля:**

| Поле | Зачем |
|---|---|
| Идентификатор студента | связать события с человеком |
| Идентификатор курса | группировка |
| Дата и время события | расчёт регулярности и динамики по неделям |
| Название события / компонент | различить просмотр, форум, сдачу, тест |
| Origin (web/ws/cli) | отсечь фоновые задачи, они не поведение людей |

**Период:** два учебных года. Ориентир — `2024-09-01 … 2026-06-30`.
Один год тоже сработает, но два дают больше наблюдений и позволяют
проверить устойчивость результата между годами. Для Q1 это заметный плюс.

---

### 1.2 Оценки

**Что это:** итоговые оценки за курс и, желательно, за отдельные задания.

**Где взять:**
- SQL — `ЗАПРОС 4`
- интерфейс — `Курс → Оценки → вкладка Экспорт → Текстовый файл (CSV)`

**Обязательные поля:**

| Поле | Зачем |
|---|---|
| Идентификатор студента | связка |
| Идентификатор курса | связка |
| Итоговая оценка за курс | **зависимая переменная** |
| Максимальный балл по курсу | нормировка к шкале 0–100 |
| Тип элемента (итоговая / за задание) | отделить итог от промежуточных |

⚠ Максимальный балл обязателен. Если в разных курсах разные шкалы
(где-то 100, где-то 5), без нормировки объединённый анализ бессмыслен.

---

### 1.3 Каталог курсов

**Где взять:** SQL — `ЗАПРОС 1`, либо `Администрирование → Курсы`

| Поле | Зачем |
|---|---|
| Идентификатор курса | ключ |
| Дата начала курса | отсчёт номера недели |
| Дата окончания | длительность |
| Категория / факультет | контроль дисциплинарных различий |
| Число студентов | отсев мелких курсов |

⚠ Дата начала критична: все недельные признаки считаются от неё.
Если у курса `startdate` не заполнен — такой курс из выборки выпадает.

---

### 1.4 Состав студентов по курсам

**Где взять:** SQL — `ЗАПРОС 2`, либо `Курс → Участники`

Нужно, чтобы отделить студентов от преподавателей и админов. Их действия
в логах перемешаны, а преподаватель заходит в курс на порядок чаще
студента — если их не убрать, статистика поедет.

⚠ Только роль «студент». В интерфейсе на странице «Участники» есть
фильтр по роли.

---

### 1.5 Задания и сроки сдачи

**Где взять:** SQL — `ЗАПРОС 5`

| Поле | Зачем |
|---|---|
| Идентификатор задания и курса | связка |
| Срок сдачи (дедлайн) | расчёт опережения |
| Фактическое время сдачи | то же |
| Статус (сдано / черновик) | отсечь незавершённые |

Из этого считается `lead_time` — за сколько часов до дедлайна сдано.
Это проверка H3 и один из самых ранних предикторов для RQ3.

# БЛОК 2. Форма обучения — вне Moodle

### 2.1 Соответствие курсов формам обучения

**Это самый недооценённый пункт списка.**

В Moodle такого признака **нет вообще**. Поле `format` в базе — это
формат отображения страницы курса (topics/weeks), а не форма обучения.

Без этой таблицы разваливается RQ2, а RQ2 — половина научной новизны
работы. Статья без него превращается из сравнительного исследования
в описательное, и это разница между Q1 и Q3.

**Где взять:** учебная часть, деканат, или тот, кто составляет расписание.

**Формат — две колонки:**

```
course_id,mode
1234,distance
1235,hybrid
1236,onsite
```

**Как просить:** сначала выполни запрос 1 и получи `courses.csv`.
Приходи в учебную часть уже со списком курсов — им останется проставить
форму напротив каждого. Это работа на час, а не исследование.

**Если форм всего две** (например только дистанционная и очная) — тоже
нормально, сравнение остаётся валидным.

**Нужен баланс:** минимум 8–10 курсов каждой формы. Если дистанционных
курсов всего три, сравнение будет статистически бессильным.

# БЛОК 3. Контрольные переменные — что отличает Q1 от Q3

Эти данные не обязательны, чтобы статья существовала. Но именно их
отсутствие чаще всего отправляет рукопись из Q1 в Q3.

### 3.1 Балл при поступлении — самый важный пункт блока

**Зачем:** без него у рецензента есть убийственный вопрос — *«вы
показали, что успешные студенты чаще заходят в LMS, или что заход
в LMS делает студента успешным? Может, и то и другое объясняется
исходной подготовкой?»*

Ответить на это можно только контрольной переменной.

**Где взять:** приёмная комиссия, деканат, отдел кадров студентов.

**Формат:**
```
student_hash,entry_score
a3f9c2e1...,182.5
```

⚠ Хешировать **той же самой солью**, что и остальные файлы. Иначе
таблицы не соединятся. Если в деканате не смогут — попроси
администратора Moodle сделать выгрузку с хешированием, он умеет.

### 3.2 Курс и направление подготовки

```
student_hash,year_of_study,program
```

Контроль: первокурсники ведут себя в LMS иначе, чем выпускники.

### 3.3 Демографические переменные — по желанию

Пол и возраст часто используются как контроли. **Но** они повышают
риск реидентификации в малых группах и усложняют согласование с
комиссией по этике.

Рекомендация: **не брать на первой статье.** Отсутствие демографии
закрывается одной строкой в Limitations и почти никогда не становится
причиной отказа. А вот утечка персональных данных — становится.

Последний пункт важен: если студенты частично работают вне Moodle,
это ограничение исследования, и его надо честно описать.

# БЛОК 5. Документы — без них не примут к рассмотрению

### 5.1 Этическое одобрение

Решение комиссии по этике вуза **с номером и датой**. Либо документ
об освобождении (exemption) для обезличенных ретроспективных данных.

Формулировка для заявки: *ретроспективный анализ обезличенных данных
учебной активности; вмешательства в учебный процесс нет; новые
персональные данные не собираются; идентификация конкретных студентов
невозможна.*

Срок рассмотрения — от двух недель до двух месяцев. **Запускай сейчас.**

### 5.2 Разрешение на доступ к данным

Документ от руководства о доступе к данным LMS для исследования.
Тот самый, о котором шла речь. Он нужен здесь — в Ethics statement,
и чтобы снять личную ответственность с администратора Moodle.

# Требования к объёму — что нужно для Q1

| Параметр | Минимум | Хорошо для Q1 |
|---|---|---|
| Курсов | 20 | 40+ |
| Наблюдений «студент × курс» | 800 | 2000+ |
| Учебных лет | 1 | 2 |
| Курсов каждой формы обучения | 8 | 15+ |
| Направлений / факультетов | 2 | 4+ |

Разнообразие важнее объёма. Данные с одного факультета — это кейс
одного факультета, и рецензент так и напишет. Данные с четырёх
факультетов — это уже про институт.

## Если чего-то не будет

Не всё критично одинаково:

| Чего нет | Последствие |
|---|---|
| Форм обучения | RQ2 выпадает, статья слабеет вдвое → переформулируем под одну форму |
| Баллов при поступлении | Серьёзное ограничение, целимся в Q2 вместо Q1 |
| Данных о заданиях | H3 выпадает, RQ3 остаётся |
| Второго года | Работает, но устойчивость не проверить |
| Демографии | Одна строка в Limitations, не проблема |

Присылай то, что есть — подстроим дизайн под реальные данные.
Идеального набора не бывает почти никогда.
